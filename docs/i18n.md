# 国际化（i18n）

用户端页面支持 `zh-CN`（默认）、`en`、`ru` 三种语言，基于 [next-intl](https://next-intl.dev) v4（App Router + 按语言前缀路由）。后台 `/admin` 只有中文，不做多语言。

## 1. 架构总览

### 1.1 URL 规则

| 地址                          | 语言  | 说明                                  |
| ----------------------------- | ----- | ------------------------------------- |
| `/`、`/gallery`、`/login`     | zh-CN | 默认语言不带前缀（`as-needed`）       |
| `/en`、`/en/gallery`          | en    |                                       |
| `/ru`、`/ru/pricing`          | ru    |                                       |
| `/zh-CN/...`                  | zh-CN | 307 重定向到无前缀地址并写 Cookie     |
| `/admin/...`                  | zh-CN | 不经过 proxy，不进入 `[locale]`       |
| `/api/...`                    | —     | 开发期 rewrites 到 Java，生产走 nginx |
| `/sitemap.xml`、`/robots.txt` | —     | 元数据路由，不经过 proxy              |

- 内部路由全部在 `src/app/[locale]/` 下；proxy 把无前缀地址内部改写为 `/zh-CN/...`，浏览器地址不变。
- `/signup` → `/register`、`/en/signup` → `/en/register` 的 308 在 `next.config.ts` 的 `redirects` 中（先于 proxy 执行）。
- 支付回跳 `/billing/result?order=...` 不带前缀，仍然有效（中文用户直接打开；其他语言用户按 Cookie 被重定向到 `/en/billing/result?...`，查询参数保留）。

### 1.2 语言协商（proxy）

`src/proxy.ts`（Next 16 中 `middleware.ts` 改名为 `proxy.ts`；项目使用 `src/app`，所以文件放在 `src/` 下与 `app` 同级）。

普通访问者请求**无前缀**地址时，按以下优先级决定语言：

1. URL 前缀（`/en/...`、`/ru/...`）——永远最高优先级，访问带前缀地址会更新 Cookie；
2. `NEXT_LOCALE` Cookie（语言切换器或上一次访问带前缀地址时写入，保留一年）；
3. `Accept-Language` 请求头；
4. 默认 `zh-CN`。

协商结果不是 zh-CN 时会 307 重定向到带前缀地址（例如英文浏览器首次访问 `/gallery` → `/en/gallery`）。

关键保证：

- **爬虫不会被重定向**：User-Agent 命中 `bot|crawl|spider|...` 的请求走 `localeDetection: false` 的实例，只认 URL：无前缀永远返回中文。所以 `/` 的中文内容可被收录，hreflang 也能互相指向。
- **主动选择中文的用户不会被带走**：切换器会写 `NEXT_LOCALE=zh-CN`，Cookie 优先于 `Accept-Language`，此后访问 `/` 一直是中文。
- `alternateLinks: false`：hreflang 由 `buildMetadata` 写进 HTML、由 sitemap 输出，不再在每个响应（包括不收录的应用页）上加 `Link` 头。

matcher：`/((?!api|admin|_next|_vercel|.*\\..*).*)`，排除 `/api`、`/admin`、内部路径和所有带点的路径（静态文件、`sitemap.xml`、`robots.txt`）。新增的公开路由如果路径里会出现点号（例如 `/users/jane.doe`），需要在 matcher 里单独加一条。

### 1.3 根布局

`src/app` 下没有 `layout.tsx`，有两个根布局：

- `src/app/[locale]/layout.tsx`：`<html lang={locale}>`、`NextIntlClientProvider`、站点级 metadata（`buildSiteMetadata`）、`generateStaticParams`（全部语言）、`dynamicParams = false`。
- `src/app/admin/layout.tsx`：`<html lang="zh-CN">`、noindex、管理员鉴权。

两者都通过 `src/components/layout/root-document.tsx` 输出 `<html>/<body>`、全局样式和主题首屏脚本，改全局结构只改这一个文件。在两个根布局之间跳转（例如登录后进入 `/admin`）是整页刷新，这是 Next 多根布局的正常行为。

404：

- `[locale]` 下未知路径由 `src/app/[locale]/[...rest]/page.tsx` 调用 `notFound()`，渲染本地化的 `src/app/[locale]/not-found.tsx`；
- 未匹配任何路由时渲染 `src/app/global-not-found.tsx`（中文，`experimental.globalNotFound`）；
- 注意：Next 16 对页面内抛出的 `notFound()` 返回 404 状态码和服务端 `<title>`/`noindex`，但正文由客户端恢复渲染（HTML 外壳为 `__next_error__`），这是框架行为，不需要处理。

错误页：`src/app/[locale]/error.tsx`、`src/app/admin/error.tsx` 共用 `components/layout/error-view.tsx`。

### 1.4 请求配置与回退

`src/i18n/request.ts`（next-intl 插件默认路径）按顺序确定语言：

1. `getTranslations({ locale })` 显式传入；
2. `next/root-params` 的 `locale`（`[locale]` 根布局下自动可用，未知值 `notFound()`）；
3. proxy 写入的请求头 / `setRequestLocale` 缓存；
4. 都没有（`/admin`、global-not-found）→ `zh-CN`。

文案回退（`src/i18n/messages.ts` + `merge-messages.ts`）：

- 以 `messages/zh-CN.json` 为底，用目标语言深度覆盖；目标语言中**缺失或空字符串**的 key 保留中文。合并结果结构永远与 zh-CN 相同，运行时不会出现 MISSING_MESSAGE。
- 开发环境每种语言首次加载时打印一次「N 条未翻译，已回退到 zh-CN」。
- `onError` / `getMessageFallback`（`src/i18n/error-handling.ts`，服务端和客户端共用；客户端通过 `IntlErrorHandlingProvider` 注入）：开发环境缺 key 打 `console.warn` 并显示 key 路径；生产环境不打印缺失、返回空字符串，**绝不把原始 key 展示给用户**。ICU 格式错误等其他错误始终 `console.error`。

### 1.5 文件布局

## 2. 在组件里使用

### 2.1 Server Component

```tsx
import { getTranslations } from "next-intl/server";

export async function PricingHeader() {
  const t = await getTranslations("pricing");
  return <h1 className="page-title">{t("title")}</h1>;
}
```

需要语言本身时用 `const locale = await getLocale()`（类型是 `"zh-CN" | "en" | "ru"`）。页面不需要再调用 `setRequestLocale`：`request.ts` 通过 `next/root-params` 拿到语言（根布局里保留了一次调用作为兜底）。

非组件场景（`generateMetadata`）同样用 `getTranslations` / `getLocale`。

### 2.2 Client Component

```tsx
"use client";
import { useTranslations } from "next-intl";

export function SubmitButton(props: SubmitButtonProps) {
  const t = useTranslations("generate.prompt");
  return <button>{props.isLoading ? t("submitting") : t("submit")}</button>;
}
```

`[locale]` 根布局已把全部 messages 下发给客户端（`NextIntlClientProvider` 自动继承 locale、messages、formats、timeZone）。如果以后客户端包体成为问题，可以在布局中用 `messages={pick(messages, [...])}` 只下发需要的命名空间。

不要把翻译后的字符串在服务端拼好再当 props 传给客户端组件（除非组件本身是通用 UI，例如 `SideNav` 接收 `label`）；业务组件直接在自己内部调用 `useTranslations`。

### 2.3 导航

用户端代码一律从 `@/i18n/navigation` 导入，路径写**不带语言前缀**的内部路径：

```tsx
import { Link, redirect, usePathname, useRouter } from "@/i18n/navigation";

<Link href="/history">...</Link>; // en 下渲染为 /en/history
router.push(`/canvas/${board.id}`);
redirect({ href: "/login", locale }); // 服务端，locale 必传（await getLocale()）
const pathname = usePathname(); // 已去掉 /en、/ru 前缀，可直接和 "/history" 比较
```

- `useSearchParams`、`notFound`、`useParams` 仍然从 `next/navigation` 导入。
- 基于当前 `next/navigation` 的 `usePathname()` 拼接查询参数再 `push` 的写法（例如 `AppPagination`）天然保留前缀，可以不改。
- 后台 `/admin` 继续用 `next/link`、`next/navigation`。用户端跳到后台必须用原生 router（`login-form.tsx` 的 `appRouter.push("/admin")`），否则会被加上 `/en` 前缀。
- `src/server/auth.ts`：`requireUser()` 跳当前语言的 `/login`；`requireAdmin()` 对非管理员跳无前缀 `/dashboard`（由 proxy 按偏好落到对应语言）。
- `mailto:`、`https://`、`#hash` 等非站内路径传给 `Link` 会原样保留。

### 2.4 ICU 参数、复数、富文本

```json
{
  "history": {
    "tasksCount": "{count, plural, other {# 个任务}}",
    "retrying": "重试中（第 {attempt} 次）",
    "agree": "我已阅读并同意<terms>服务条款</terms>"
  }
}
```

```tsx
t("tasksCount", { count: 3 });
t("retrying", { attempt: 2 });
t.rich("agree", { terms: (chunks) => <Link href="/terms">{chunks}</Link> });
```

- 英文、俄文的复数类别不同：en 需要 `one`/`other`，ru 需要 `one`/`few`/`many`/`other`。zh-CN 只写 `other`，翻译时由译者补全：
  `"{count, plural, one {# task} other {# tasks}}"`、`"{count, plural, one {# задача} few {# задачи} many {# задач} other {# задачи}}"`。
- 数字参数会按语言格式化（en 下 `2026` 会变成 `2,026`）。年份、编号这类不应加千分位的值传字符串。
- 不要用字符串拼接组装句子（`t("a") + name + t("b")`），语序在不同语言里不同；用一个带参数的完整句子。
- 参数类型由 `messages/zh-CN.d.json.ts` 推导，漏传参数或写错 key 都会让 `pnpm typecheck` 失败。

### 2.5 日期、数字、货币

统一走 next-intl 的格式化器，不再直接写 `new Intl.DateTimeFormat("zh-CN")`、`toLocaleString()` 或 dayjs 格式串：

```tsx
// Server
const format = await getFormatter();
// Client
const format = useFormatter();

format.dateTime(parseJavaDateTime(item.createdAt), "datetime"); // 2026/10/25 23:54
format.dateTime(parseJavaDateTime(item.createdAt), "short"); // 2026/10/25
format.dateTime(date, "monthDay"); // 10/25
format.number(order.points, "points"); // 12,345
format.number(order.amount, "currency"); // ¥99.00 / CN¥99.00
format.relativeTime(date, now); // 3 分钟前（now 来自 useNow）
```

共享格式定义在 `src/i18n/formats.ts`（`dateTime.short / monthDay / datetime / time`，`number.points / currency / percent`），格式名有类型检查。需要新格式时加在这里，不在组件里内联 `Intl` 选项。

**Java 时间**：Java `LocalDateTime` 返回不带时区的 `2026-10-25T23:54:22`，语义是北京时间。直接 `new Date(value)` 会按运行环境时区解析（服务端 UTC、浏览器本地时区），结果不一致。一律先 `parseJavaDateTime(value)`（`src/utils/java-time.ts`，补 `+08:00`），再交给格式化器；格式化器的 `timeZone` 固定为 `Asia/Shanghai`，所以所有语言、所有环境展示的都是北京时间。

## 3. Key 命名约定

- 命名空间按区域/页面划分，第一层固定从下表选择，需要新命名空间时先在这里登记：

| 命名空间      | 内容                                                                             |
| ------------- | -------------------------------------------------------------------------------- |
| `common`      | 跨页面共享的按钮/动作（`common.actions.*`）、状态词（`common.status.*`）、品牌名 |
| `nav`         | 顶栏、侧边栏、账户菜单、语言/主题切换、公告                                      |
| `auth`        | 登录、注册、找回密码、滑块验证（`auth.login.*`、`auth.register.*`…）             |
| `landing`     | 首页                                                                             |
| `gallery`     | 公开画廊、投稿按钮                                                               |
| `pricing`     | 定价页                                                                           |
| `docs`        | 文档页框架文案（文档正文来自后台配置）                                           |
| `licenses`    | 开源许可页                                                                       |
| `dashboard`   | 概览、签到                                                                       |
| `generate`    | 图片生成工作区                                                                   |
| `canvas`      | 无限画布、局部重绘                                                               |
| `video`       | 视频创作                                                                         |
| `history`     | 创作历史                                                                         |
| `favorites`   | 收藏合集                                                                         |
| `submissions` | 我的投稿                                                                         |
| `credits`     | 积分购买                                                                         |
| `billing`     | 订单、支付结果                                                                   |
| `tickets`     | 意见反馈                                                                         |
| `settings`    | 账户设置                                                                         |
| `errors`      | 错误页、404、接口错误（`errors.api.*`）                                          |
| `metadata`    | 每个页面的 `<title>` / description（`metadata.<page>.title`）                    |
| `ui`          | 通用 UI 组件（分页、选择器、灯箱等）                                             |

- key 用 camelCase 的**语义名**，描述用途而不是内容：`generate.prompt.placeholder`、`billing.status.paid`、`history.empty.title`。**禁止**用中文原文或其拼音做 key。
- 层级：`<命名空间>.<区块>.<元素>`，一般不超过 4 层。同一组件的文案放在同一个区块下。
- 枚举值（状态、分类、模型质量等）用后端值作为最后一级：`billing.status.<status>`、`gallery.category.<category>`，组件里 `t(\`status.${order.status}\`)`；前端 `utils/*` 里现有的中文 label 映射表迁移为 key 映射。
- 只出现一次的通用词也优先复用 `common.*`；页面里语义不同的同形词（例如「生成」作为按钮 vs 作为状态）分开写。
- 动态拼接 key（``t(`items.${key}`)``）只在 key 集合是固定联合类型时使用（参考 `product-frame.tsx`、`constants/landing.ts`），这样类型检查仍然有效。
- 用户创作内容、后台配置内容（公告、文档正文、套餐名称/描述、模型名）不进翻译文件，原样展示。

## 4. 新增页面清单

1. 路由放在 `src/app/[locale]/...`；登录后的页面放 `(product)`，认证页放 `(auth)`。
2. 所有可见文案、`aria-label`、`title`、`alt`、`placeholder`、toast/校验提示写进 `messages/zh-CN.json`，en/ru 放相同 key（暂未翻译可以留空字符串，或者先不加）。
3. 站内跳转用 `@/i18n/navigation`。
4. 日期/数字/金额用格式化器；Java 时间先 `parseJavaDateTime`。
5. 公开页导出 `generateMetadata` 并使用 `buildMetadata`（见 [docs/seo.md](./seo.md)），并把路径加到 `src/lib/site-routes.ts` 的 `publicPages`；应用页继承 `(product)` 布局的 noindex，可选地用 `metadata.<page>.title` 设置标题。
6. 检查长文案布局（见第 8 节）。
7. `pnpm check`。

## 5. 新增语言（以德语 `de` 为例）

1. `src/i18n/routing.ts`：`locales` 加 `"de"`，`localeNames` 加 `de: "Deutsch"`，`openGraphLocales` 加 `de: "de_DE"`。TypeScript 会提示所有需要补齐的 `Record<AppLocale, ...>`。
2. `src/i18n/messages.ts`：`loaders` 加 `de: () => import("../../messages/de.json")`。
3. 新建 `messages/de.json`（可以先写 `{}`，运行时全部回退到中文）。
4. 如果需要 antd 组件的本地化（分页、日期选择器），在使用 `ConfigProvider` 的地方按 locale 选择 `antd/locale/de_DE`。
5. `pnpm i18n:check` 查看缺失数量；`pnpm check`。
6. 不需要改 proxy matcher、sitemap、robots、hreflang：它们都从 `routing.locales` 生成。
7. 如果新语言是从右到左书写（ar、he）：在 `[locale]/layout.tsx` 给 `RootDocument` 传 `dir`，并确认第 8 节的逻辑属性规则已遵守。

## 6. 检查与工作流

```bash
pnpm i18n:check            # 结构检查；每种语言列出最多 20 条缺失 key
pnpm i18n:check --verbose  # 列出全部缺失 key
```

- 缺失/空字符串的翻译：**警告**，不影响退出码（运行时回退中文）。
- en/ru 中出现 zh-CN 没有的 key、结构不一致、JSON 无法解析、zh-CN 自身为空：**错误**，退出码 1。
- 已加入 `pnpm check`（在 typecheck 之后）。

翻译流程：

1. 开发时只写 zh-CN（完整、准确），en/ru 放相同 key 的空字符串或者不加。
2. 定期批量翻译：`pnpm i18n:check --verbose` 导出缺失清单，交给译者/翻译工具补齐 en.json、ru.json。
3. 翻译时注意 ICU 复数类别（ru 需要 one/few/many/other）、保持占位符和富文本标签不变。
4. 改 zh-CN 文案含义时，同步清空对应 en/ru 值，让它重新进入待翻译清单。

## 7. 后端消息

现状：Java 返回中文 `message`，前端原样展示。

目标模式：

1. 后端为可预期的业务错误增加稳定的字符串错误码 `errorCode`（例如 `AUTH_INVALID_CREDENTIALS`、`POINTS_INSUFFICIENT`），`code` 继续表示 HTTP 语义；
2. 前端在 `src/i18n/api-error.ts` 的 `errorCodeKeys` 中把已知 `errorCode` 映射到 `errors.api.*` 文案；未知的码回退显示后端 `message`；
3. 前端每个请求都带 `Accept-Language`（`src/utils/request.ts` 读取 `<html lang>`），后端可据此返回对应语言的 `message`，作为未登记错误码时的兜底。

已经实现的前端部分：

- `request.ts`：自动添加 `Accept-Language`（调用方显式传入时不覆盖）；`ApiRequestError.errorCode` 读取响应中的字符串 `errorCode`（后端未提供时为 `undefined`），其他行为不变。
- `translateApiError(error, t)`：

```tsx
const tError = useTranslations("errors.api");
try {
  await authApi.loginWithEmail(form);
} catch (error) {
  setMessage(translateApiError(error, tError));
}
```

顺序：已登记 `errorCode` → 网络失败（`code === 0`）→ 后端 `message` → `errors.api.unknown`。

- 迁移时把现有的 `getErrorMessage(error)` 展示逻辑替换为 `translateApiError`。`request.ts` 内部的兜底中文（「服务端返回格式不正确」等）属于网络层异常，后续可改为抛出固定 `errorCode` 再由这里翻译。
- SSR 侧 `requestJava`（`src/server/java-api.ts`）目前未转发语言；需要时从 `getLocale()` 取值加 `Accept-Language` 头。

## 8. 长文案与布局规则

同一句话的俄文通常比中文长 2–3 倍，比英文长约 40%。在迁移组件时一并检查：

- 按钮、标签、导航项**不设固定 `width`**，用 `min-width` + 左右 `padding`（参考 `.productTopNav__login`）；需要单行时加 `white-space: nowrap`。
- 空间受限且必须单行的位置（表格单元、卡片标题、侧边栏项）用 `min-width: 0` + `overflow: hidden` + `text-overflow: ellipsis`，并在元素上加 `title` 展示完整文本；侧边栏和卡片正文允许换行。
- 水平排列的一组链接/标签要允许滚动或换行（`overflow-x: auto` / `flex-wrap: wrap`），不要假设只占一行（参考 `.productTopNav__mobileNav`）。
- flex 子项里放文本时记得 `min-width: 0`，否则长单词会把容器撑开。
- 不要在文案里用空格/换行控制排版，不要把多段文案拆成多个 key 再拼接。
- 为将来可能的 RTL 语言，新写的样式优先使用逻辑属性：`margin-inline-start`、`padding-inline`、`inset-inline-end`、`text-align: start`；图标方向（箭头）不要硬编码含义。
- 改完后至少用 `/ru/...` 在桌面和 390px 宽度下各看一次。

## 9. 后台例外

`/admin` 与 `src/features/admin/**` 只有中文，允许直接写中文字符串，继续使用 `next/link`、`next/navigation`。后台复用的用户端组件（顶栏、账户菜单、`SideNav`）通过 next-intl 拿到 zh-CN 文案；后台顶栏不显示语言切换器（`<ProductTopNav isAdminConsole />`）。
